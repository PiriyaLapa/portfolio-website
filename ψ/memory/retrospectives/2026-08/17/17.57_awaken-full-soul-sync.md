## Honest Feedback

Three friction points, specific to this session. First: the `&&`-chained
system-check command broke on the first check (git rev-parse) precisely
because it was expected to fail per already-known context — should have
either used `;` for independent checks or just skipped the redundant
git-repo check entirely since the answer was already known. Second: `ghq
get -u` on `oracle-v2` hit a 2-minute timeout on `git submodule update
--init --recursive`, even though the actual `git pull --ff-only` had
already completed — the clone wasn't actually stuck, but the tool call
looked like a hard failure until I checked `git status` directly. Cost a
few extra round trips to diagnose. Third: the awaken skill's own
instructions point family study at `oracle-v2#17 --comments`, which turned
out to be a retired convention — the correct, current pointer only surfaced
by reading `arra-oracle-v3#60`'s body text, which happens to document its
own supersession. That's arguably fine (discovery is the point) but it
means the skill file itself has drifted slightly out of date from the
process it describes.

## Lessons Learned

- When a CLAUDE.md already has a complete, coherent Oracle Identity but the
  git repo / `ψ/` infrastructure is missing, don't default to re-running the
  wizard from zero — surface the mismatch explicitly and let the human
  choose whether to complete the interrupted birth or start over. Silently
  picking either path risks either redundant re-answering or clobbering
  real prior thought.
- Before chaining shell commands with `&&`, check whether the environment
  info already answered one of the checks in the chain — chaining after a
  known-failing check wastes a round trip for no benefit.
- Treat instructions inside a ritual/skill file that point at a specific
  external artifact (an issue number, a URL) as a starting pointer, not
  ground truth — verify against the current live source before acting,
  since those pointers drift out of date faster than the skill file gets
  updated.
