## Lessons Learned

- **When adapting a dev-process pattern from a sibling/parent project, map it
  against the target repo's actual complexity surface before porting — don't
  default to structural parity.** Lumine's 7 agent roles exist because it has
  a backend, a DB schema, auth, and a test suite; portfolio-website has none of
  those, so 4 of the 7 roles had no real target here. The valuable move wasn't
  "translate all 7," it was identifying which 3 mapped to this project's actual
  recurring risks (confidentiality leaks, design-token drift, deploy
  verification without a browser) and skipping the rest explicitly, with the
  skip reasoning stated out loud rather than left implicit.
- **A scope-separation rule you apply to justify one branch/PR split should be
  applied to every concurrent piece of unrelated work in the same session, not
  just the one where it's top of mind.** If dev-tooling and content-bookkeeping
  are different enough concerns to deserve separate branches once, that logic
  doesn't stop applying to the next commit just because a branch is already
  checked out.
